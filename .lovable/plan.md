# Фаза 3 — роли: клиент, специалист, администратор, владелец

## Что есть сейчас

- Вход: страница `/auth` (Google, Apple, email+пароль, восстановление пароля) на Lovable Cloud Auth.
- Роли: таблица `user_roles` (admin / user), проверка `is_admin()`, при регистрации профиль создаётся автоматически.
- Закрытые разделы: личный кабинет, профиль, приложение базы персон, управление сайтом (CMS) и управление пользователями — последние два только для администратора.
- В управлении пользователями: имя, почта, роль (Администратор/Пользователь), дата, блокировка, «Открыть базу».
- Журнала изменений ролей нет, выбора роли при регистрации нет.

## Что будет добавлено

### 1. Новые данные (ничего существующего не трогаем)

- Хранилище продуктовой роли пользователя: «клиент» или «специалист». Если записи нет — считается клиентом.
- Хранилище признака владельца. Закрыто наглухо: читать и менять можно только через защищённые серверные функции.
- Журнал изменений ролей: кто, кому, что изменил и когда. Видит только владелец.
- Первым владельцем становится текущий администратор проекта (назначается один раз внутри миграции, без email в коде сайта).

### 2. Правила определения роли

Порядок: владелец → администратор → специалист → клиент. Существующая проверка администратора остаётся источником админ-доступа; владелец дополнительно получает админ-права.

### 3. Выбор роли при регистрации

На странице регистрации появляется выбор: «Я клиент» (по умолчанию) или «Я специалист». Роль сохраняется после входа один раз и сама по себе больше не меняется. Если роль не выбрана — при первом входе в личный кабинет появится короткий вопрос «Клиент или специалист?». Механика почты, пароля и восстановления не меняется.

### 4. Отображение роли

Роль показывается в профиле и в личном кабинете (Клиент / Специалист / Администратор / Владелец, RU и EN через текущую локализацию).

### 5. Управление ролями

Страница управления пользователями расширяется:

- администратор видит всё как сейчас (список, блокировка, открыть базу) плюс колонку роли;
- владелец дополнительно получает действия: сделать клиентом, сделать специалистом, назначить/снять администратора, назначить владельца, снять владельца (с подтверждением), а также создать учётную запись (почта, имя, пароль, роль клиент/специалист) и удалить учётную запись (с подтверждением, кроме себя и владельцев);
- снять владельца с себя нельзя, последнего владельца снять нельзя, назначать владельца может только владелец.

Все действия идут через серверные проверки, не через прямые запросы из браузера. Каждое действие показывает загрузку, успех или ошибку.

### 6. Доступы

Клиент и специалист не видят управление сайтом, управление пользователями и владельческие действия. Приложение базы персон и его маршрут не меняются.

## Технические детали

- Миграция (`create table if not exists`, без удалений):
  - `public.user_product_roles` — `user_id` PK → `auth.users`, `product_role` text check ('client','specialist') default 'client', `created_at`, `updated_at` + триггер `update_updated_at_column`.
  - `public.user_owner_flags` — `user_id` PK, `is_owner` boolean default true, timestamps.
  - `public.role_audit_logs` — `id`, `actor`, `target`, `action`, `details` jsonb, `created_at`.
  - GRANT: `user_product_roles` — select/insert для `authenticated`, all для `service_role`; `user_owner_flags` и `role_audit_logs` — только `service_role` (доступ через SECURITY DEFINER-функции).
  - RLS включён везде. Политики `user_product_roles`: select — свой или `is_owner()`; insert — `auth.uid() = user_id`; update/delete — только `is_owner()`. У `user_owner_flags` и `role_audit_logs` прямых политик для пользователей нет.
- Функции (SECURITY DEFINER, `set search_path = public`, execute только `authenticated`):
  `is_owner()`, `current_app_role()` (owner → admin через существующий `is_admin()` → specialist → client), `register_product_role(text)` (insert … on conflict do nothing), `set_user_product_role(uuid,text)`, `set_user_admin(uuid,boolean)`, `set_user_owner(uuid,boolean)` (защита от снятия себя и последнего владельца; при назначении владельца выдаётся и роль admin в `user_roles`), `owner_list_users()` — возвращает профиль + продуктовую роль + признаки admin/owner, проверяя владельца. Все владельческие функции пишут в `role_audit_logs`.
  Существующая `is_admin()` и таблица `user_roles` не изменяются; `user_roles` пишется только внутри definer-функций (прямой клиентский INSERT по-прежнему закрыт).
- Seed первого владельца: внутри миграции — пользователь с ролью admin и наименьшим `created_at` в `profiles`.
- Клиентская часть:
  - `src/lib/roles.ts` — хук `useAppRole()` (rpc `current_app_role`) + подписи RU/EN.
  - `src/routes/auth.tsx` — радиогруппа выбора роли в режиме регистрации, `signUp` с `options.data.product_role`, после появления сессии вызов `register_product_role`.
  - `src/routes/_authenticated/account.tsx` — мягкий запрос роли, если записи нет; показ роли.
  - `src/routes/_authenticated/profile.tsx` — роль из `current_app_role` вместо «Администратор/Пользователь».
  - `src/lib/users.functions.ts` — серверные функции владельца (`ownerListUsers`, `setProductRole`, `setAdmin`, `setOwner`) поверх RPC, с проверкой на сервере.
  - `src/routes/_authenticated/admin/users.tsx` — колонка роли и владельческий блок действий.
- Не меняются: настройки авторизации, подключение к базе, переменные окружения, `.env`/`.env.example`, существующие таблицы и политики, маршрут приложения базы персон, CMS-логика.

## Проверка

Регистрация клиентом и специалистом, вход, восстановление пароля, доступ администратора к CMS, отсутствие админ-разделов у клиента/специалиста, владельческие действия и все запреты (себя не снять, последнего владельца не снять, роль сам не меняет).
