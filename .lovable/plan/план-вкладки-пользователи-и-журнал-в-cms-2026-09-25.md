# План: вкладки «Пользователи» и «Журнал» в CMS

## Цель
Встроить управление пользователями и журнал действий в единую панель CMS (`/admin/cms`), довести аудит до полного системного лога с экспортом CSV — как в эталонной спецификации (вкладки 07 и 10).

## Этап 1 — Расширение аудита в базе

1. Расширить таблицу `role_audit_logs` до общего журнала действий:
   - добавить колонки `category` (roles / users / leads / cms / orders) и `actor_email`, `target_email` (денормализованные снимки, чтобы записи не терялись после удаления пользователя).
   - таблица остаётся закрытой для клиентских запросов (fail-closed, как сейчас).
2. SECURITY DEFINER-функции:
   - `list_audit_logs(limit, offset, category_filter)` — чтение журнала для владельца и администратора.
   - `log_action(category, action, target, details)` — внутренняя запись событий.
3. Подключить запись событий к существующим действиям:
   - создание и удаление учётных записей (в `createUserAccount` / `deleteUserAccount` — сейчас не пишутся в журнал);
   - блокировка/разблокировка (`setUserBlocked`);
   - изменение статусов заявок (leads) — при появлении вкладки «Заявки».
   - Смены ролей уже пишутся — оставить как есть.

## Этап 2 — Вкладка «Пользователи» в CMS

1. Перенести содержимое страницы `/admin/users` в компонент `UsersTab` (src/components/site/cms/UsersTab.tsx) и добавить вкладку «Пользователи» в CmsPanel.
2. Маршрут `/admin/users` сохранить как редирект/обёртку на CMS — старые ссылки не ломаются.
3. Возможности вкладки (всё уже есть в логике, переносится UI):
   - таблица: имя, email, роль (Владелец/Администратор/Специалист/Клиент), статус (Активен/Заблокирован), дата регистрации;
   - владельцу: смена продуктовой роли, назначение/снятие администратора и владельца, создание и удаление учётных записей;
   - администратору: блокировка/разблокировка.

## Этап 3 — Вкладка «Журнал» в CMS

1. Новый компонент `JournalTab` (src/components/site/cms/JournalTab.tsx) + вкладка «Журнал» в CmsPanel.
2. Таблица событий: дата и время (с секундами), кто совершил (email), категория, тип действия, детали.
3. Фильтр по категории и поиск по email; постраничная загрузка.
4. Кнопка «Экспорт .CSV» — выгрузка журналa в CSV прямо из браузера.
5. Доступ: владелец и администратор.

## Этап 4 — Проверка и документация

1. Typecheck + Playwright: вход владельцем, смена роли, создание/удаление учётной записи, появление записей в журнале, экспорт CSV.
2. Обновить legacy/ANNULI_PROJECT_DOCUMENTATION.md (v5.0), roadmap.md и память проекта.

## Что НЕ меняется
- Авторизация, регистрация, восстановление пароля, настройки Supabase Auth.
- Существующие таблицы, RLS-политики, роли и логика доступа (кроме добавления колонок в `role_audit_logs`).
- Защищённые маршруты, кабинеты, `/app`, CMS-вкладки «Тексты/Блоки/Изображения/Дополнения».
- Переменные окружения, .env, .env.example. Никаких секретов в клиентском коде.

## Технические детали
- Миграция: `ALTER TABLE role_audit_logs ADD COLUMN category text NOT NULL DEFAULT 'roles', ADD COLUMN actor_email text NOT NULL DEFAULT '', ADD COLUMN target_email text NOT NULL DEFAULT ''` + новые SECURITY DEFINER-функции с `SET search_path = public`.
- CSV-экспорт: генерация Blob на клиенте из данных `list_audit_logs`, без серверных зависимостей.
- CmsPanel: тип `Tab` расширяется до `"texts" | "sections" | "assets" | "addons" | "users" | "journal"`.
