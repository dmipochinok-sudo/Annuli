## 1. Purpose

Annuli — однофайловое HTML-приложение (без бэкенда) для ведения
генеалогической базы данных семьи Починок/Поберских/Гринёвых и др. Всё
хранится локально в браузере через IndexedDB. Проект некоммерческий, для
личного использования одним человеком — Дмитрием, который оцифровывает
документы (метрические книги, свидетельства, фотографии) и записывает устные
воспоминания родственников, сохраняя их в структурированном виде, пока это
ещё возможно.

Он нетехнический и делегирует все инженерные решения Claude, общаясь
краткими подтверждениями («продолжай»). Из этого следует нестандартное для
софтверного проекта ограничение: **у проекта нет постоянного разработчика с
памятью.** Каждая сессия Claude, которая берётся за задачу, восстанавливает
контекст заново — по этому документу и по коду. Архитектурные решения нужно
оценивать в первую очередь по тому, насколько быстро и надёжно их поймёт
следующая такая сессия, а не по классическим метрикам вроде связанности
модулей.

## 2. Vision

Успехом для этого проекта считается **не** «идеально спроектированный
монолит» и не количество удалённых строк кода при рефакторинге. Правильное
направление движения проверяется четырьмя условиями, которые должны
выполняться после каждой итерации:

1. документация полностью соответствует коду (ни один факт в ней не
   расходится с реальным файлом на момент сдачи);
2. всё больше бизнес-логики становится независимой от браузера (растёт доля
   Core-функций в Реестре — раздел 5);
3. уменьшается количество скрытых зависимостей, побочные эффекты
   локализованы в ограниченном списке мест (раздел 4.5);
4. **новая LLM-сессия способна понять текущее состояние проекта, прочитав
   только три файла** — этот документ, `Annuli_vX.Y.html` и `data.json` — без
   доступа к памяти о прошлых чатах.

Четвёртый пункт — ключевой. Непрерывность разработки Annuli обеспечивается
не долговременной памятью модели, а качеством и полнотой этих трёх
артефактов.

Отдельно от архитектуры: успех для самого продукта — данные семьи сохранены,
обогащаются со временем (новые сканы, расшифровки, воспоминания) и никогда
не теряются при экспорте/импорте/миграции.

## 4. Architecture

Интерфейс полностью на русском языке, в духе macOS/iOS (system fonts,
скруглённые карточки, светлая/тёмная тема), с v2.6/v2.8 — полноценная
мобильная адаптация от 375×812px (off-canvas сайдбар, горизонтальный скролл
панелей, touch pan/zoom в дереве и лайтбоксе).

### 4.1 Storage (IndexedDB)

```js
const DBN='genealogy_db', DBV=2, DST='persons', IST='images';
```

Два object store:

1. **`persons`** (`keyPath:'id'`) — все персоны целиком (модель — раздел 6).
2. **`images`** (`keyPath:'id'`) — бинарные `Blob` изображений документов и
   аватаров, индексируются `imageId` (строка вида `img_xxxxxxxx`), которая
   хранится внутри объекта персоны в массивах `*DocPages[]` и в поле
   `avatarImageId`.

```js
imgPut(id, blob)          // сохранить Blob
imgGet(id)                 // получить Blob напрямую (не {id,blob,name})
imgDel(id)                 // удалить
imgAllKeys()                // все ключи store images (используется для сборки мусора)
makeBlobURL(blob)           // URL.createObjectURL + учёт в _objURLs для revokeAllObjURLs()
```

Ключевая деталь: **полноразмерные изображения физически не хранятся внутри
объекта персоны** — только `imageId`-ссылка. В самой персоне остаётся лишь
`avatarThumb` — маленькая base64-миниатюра (для сайдбара и быстрого
предпросмотра без похода в `images` store).

Сборка мусора неиспользуемых Blob'ов — в `init()`, через 20 секунд после
загрузки: сравнивает все `imgAllKeys()` с `collectImageIds()` по всем
персонам (плюс текущей открытой несохранённой) и удаляет несовпавшие.

### 4.2 Форма персоны (вкладки)

```js
const tabs=[
  ['t1','Основные данные'],   // фото, идентификация, ФИО, рождение+документ, смерть+документ
  ['t2','Родители'],           // отец, мать, воспреемники (крёстные)
  ['t3','Братья и сёстры'],    // подсказки buildSug (с v2.8, в sibSugBox) + места жительства
  ['t4','Семья'],              // браки + дети (объединены), подсказки buildChildSug в childSugBox
  ['t5','Архив'],              // произвольные прикреплённые документы (mkDoc)
  ['t6','Биография'],          // военная служба (+docId с v2.7) + воспоминания
];
```

Рендерятся ВСЕ шесть вкладок сразу в `buildForm()` (не лениво), активная —
без класса `hidden`, остальные — с ним; `swTab(id,btn)` переключает класс и
`.tbtn.on`. Активная вкладка хранится в глобальной `let activeTab='t1'` и
переживает переключение режима редактирование↔просмотр и сохранение —
сбрасывается на `'t1'` только в `selP()` (выбор другой персоны) и
`newPerson()` (создание новой). **Это первый кандидат на переезд в
`AppState`, когда до него дойдёт очередь (Roadmap, Этап 2).**

**Изменение с v2.8**: подсказки «возможные братья/сёстры» (`buildSug`)
перенесены из вкладки «Родители» (`t2`) во вкладку «Братья и сёстры» (`t3`),
обёрнуты в `<div id="sibSugBox">` для точечного перерендера без пересборки
всей вкладки. Аналогично дети из подсказок (`buildChildSug`) — в
`<div id="childSugBox">` на `t4`. Персоны, добавленные из блока подсказок
(`addSugSib`/`addSugChild`), сразу пропадают из списка кандидатов — `buildSug`
и `buildChildSug` исключают тех, чей `id` уже есть среди `linkedId` в
`p.siblings`/`p.children` соответственно.

### 4.3 Ключевая бизнес-логика (по подсистемам)

**Дедупликация при сохранении** (`savePerson()` → `findPendingDuplicates()`):
для несвязанных (`fatherLinkedId`/`motherLinkedId`/`sibling.linkedId`/
`child.linkedId`/`marriage.spouseLinkedId` пустые) но заполненных по ФИО
полей ищутся кандидаты в `all` с совпадающим именем/фамилией. Если найдены —
модалка `dupeModal` с выбором «привязать к существующей» / «создать новую»
на каждую позицию, дальше `confirmDupeAndSave()` → `applyDupeResolutions()` →
`finalizeSave()`.

**`finalizeSave()`** — после `dbPut(cur)`:
1. синхронизирует список `marriages` со стороны супруга (создаёт обратную
   запись о браке, если её ещё нет);
2. `promoteUnlinkedRelatives(cur)` — если родитель/брат-сестра по ФИО
   совпадает с кем-то в базе, но не был связан явно — добавляет обратную
   ссылку без создания новой персоны;
3. **(с v2.8)** `createMissingRelativePersons(cur)` — для родителей,
   братьев/сестёр, детей и супругов, у которых заполнено ФИО, но связи так и
   не появилось ни вручную, ни через диалог дедупликации, ни через
   `promoteUnlinkedRelatives` — создаёт заглушечную персону (`mkP()` +
   минимум полей, с эвристикой пола для родителя/супруга и сдвигом поколения
   `shiftGeneration(gen, ±1)`) и связывает её автоматически. Идемпотентна,
   не перезаписывает существующие связи, новые персоны создаются без
   `personIndex` — пользователь присваивает вручную.

**Дерево** (`buildFamilyGraph()` → `renderTree()`): строит граф по persons +
явным (`*LinkedId`) и подразумеваемым по ФИО связям, располагает по
поколениям, центрирует ряды на общей вертикальной оси.
`enforceSpouseAdjacency()` (с v2.7) — финальный проход, гарантирующий, что
супруги всегда стоят рядом в ряду поколения, независимо от того, как они
изначально попали в последовательность (по родителю или как «сирота»).

**Поиск** (`showSearchResults()`): полнотекстовый по всем персонам через
`personSearchSegments(p)` — плоский список `{label, text}` по всем текстовым
полям персоны (включая расшифровки документов, воспоминания), с подсветкой
совпадений (`highlightSnippet`).

Сводная карта подсистем (Responsibility / Dependencies / Side Effects) —

### 4.4 Экспорт/импорт/GEDCOM

**Экспорт (`exportDB()`)** — ZIP через встроенный JSZip 3.10.1: `data.json`
(персоны + мини-аватар в base64, БЕЗ полноразмерных фото) + `images/` с
оригинальными Blob'ами, названными по номеру документа в базе
(`sanitizeFileBase(personIndex или docId)` + `_2`/`_3` для многостраничных).
`_file`-поле временно добавляется в JSON только на время экспорта
(`ep._avatarFile`, `pg._file`), не хранится в реальной БД.

**Импорт (`prepImport()` → `doImport()`)**: принимает `.zip` (новый формат),
legacy `.json` с base64 `_imgs` (обратная совместимость через
`dataURLtoBlob2`), и старый текстовый `.json` без изображений. Режимы
`add`/`replace`. `restoreImagesForPerson()` восстанавливает Blob'ы из ZIP по
`_file`-путям, `stripImportHelperFields()` подчищает служебные поля перед
`dbPut`.

**GEDCOM (`parseGEDCOM()` → `doGEDCOM()`)**: собственный построчный парсер
(без сторонних библиотек), строит `indiMap`/`famMap`, конвертирует в формат
Annuli через `gedParseIndi()`/`gedParseFam()`/`gedDate()`.

**Инлайн-зависимость:** JSZip 3.10.1 (`dist/jszip.min.js`, UMD-сборка,
~95 КБ) вшит целиком отдельным `<script>` перед основным кодом приложения —
установлен как `window.JSZip`. Получен через `npm pack jszip@3.10.1` (домен
`registry.npmjs.org` в вайтлисте контейнера Claude); при обновлении версии —
тот же путь: скачать, извлечь `dist/jszip.min.js`, вставить как отдельный
`<script>` перед `'use strict';` основного скрипта. Не менялось с v2.3.

**Как тестировалась логика экспорта/импорта** (образец методологии для
новых Core-модулей — см. Development Rules, раздел 7): т.к.
IndexedDB/File API недоступны в Node напрямую, функции извлекались из
реального файла построчным поиском парных скобок (не переписывались вручную
— тестируется ровно тот код, что уходит в прод) и гонялись в изолированном
Node-харнессе с фейковыми `imgGet`/`imgPut`/`dbPut`/`document`, реальным
JSZip (через `dist/jszip.min.js`, требуемый как CJS-модуль) и Node-`Buffer`
вместо браузерного `Blob` на входе теста (сам прод-код от этого не зависит —
`restoreImageFromZip` всегда явно создаёт `new Blob([...])`). Проверено и
актуально: корректные имена файлов, побайтовая идентичность после
экспорт→импорт в чистое хранилище, отсутствие `_file` в персистентных
записях, обратная совместимость со старым base64-`_imgs` форматом.

### 4.5 Границы побочных эффектов

Правило: **в проекте должно быть ограниченное, явно перечислимое число мест,
где разрешены побочные эффекты.** Всё остальное — обычные вычисления над
значениями (см. Development Rules п.4, «чистая функция»).

Разрешённые категории побочных эффектов и где именно они живут:

| Категория | Где | Функции-точки входа |
|---|---|---|
| DOM | UI-слой (`show*`, `render*`, `col*`, обработчики `on*`) | ~89 функций, см. Реестр |
| IndexedDB | Storage-слой | `openDB`, `dbAll/Put/Del`, `imgGet/Put/Del`, `imgAllKeys` |
| File/Blob API | Экспорт/импорт, загрузка сканов | `onAvatarFile`, `onPageFile`, `exportDB`, `prepImport` |
| Browser download | Экспорт | `dlTxt`, ссылка `<a download>` в `exportDB` |
| `localStorage` | Тема оформления | `toggleTheme` (единственное место) |
| Время/случайность | Фабрики моделей, id | `uid()`, `new Date().toISOString()` — сознательно не инжектируются (Development Rules п.4) |

Всё, что не попадает в эту таблицу, должно быть чистой функцией. Если при
рефакторинге обнаруживается побочный эффект вне этого списка — либо
переносить его в один из существующих слоёв, либо добавлять новую строку в
эту таблицу осознанно (не молча).

## 5. Core Registry

Полный список из 183 функций верхнего уровня. Сгенерирован механическим
анализом `Annuli_v2.8.html` (скрипт: разбить файл по top-level
`function`/`async function` объявлениям, проверить тело каждой на
обращения к `document.`/`getElementById`/`querySelector`/`innerHTML`/
`classList`/`localStorage` → DOM; `indexedDB`/`db.transaction` → Storage;
иначе — Core). Эвристика приблизительная (например, функции-шаблонизаторы
вроде `pageItem()` строят HTML-строки без обращения к `document`, поэтому
попадают в Core, хотя по смыслу это View — см. примечание ниже), но даёт
честную количественную картину без ручного разбора всех функций.

**Итог**: 183 функции → **86 Core** (47%), **89 DOM** (49%), **8 Storage/IDB**
(4%). Почти половина логики уже не трогает DOM напрямую — лучшая стартовая
точка для Extract Core, чем можно было ожидать от проекта, который никогда
не проектировался слоями.

Столбец «Тест» — есть ли зафиксированный прецедент прогона этой функции
(или кода, извлечённого из неё) через Node-харнесс в прошлых сессиях.
Столбец «Статус» — `Stable` по умолчанию (всё перечисленное уже в проде и
работает), кроме явно отмеченных `Deprecated` (мёртвый код, см. Backlog).
Список «протестировано» велся по памяти проекта и может быть неполным в обе
стороны — при сомнении просто прогнать функцию через харнесс заново, это
дёшево.

> **Примечание про «Core» вьюхи-темплейтеры.** Функции вроде `pageItem()`,
> `rmarriages()`, `rchilds()`, `t1()`–`t6()` формально попадают в Core по
> эвристике (нет `document.*` внутри тела), потому что строят HTML **строкой**
> через шаблонные литералы и не трогают DOM сами — их результат подставляется
> через `innerHTML` вызывающим кодом. Технически они уже тестируемы в Node
> (сравнение возвращаемой строки), но это низкий приоритет — их баги обычно
> видны визуально сразу, а не скрытые.

## 6. Data Model

Не просто дамп JSON-полей — сначала инварианты, которые нельзя нарушать при
любом рефакторинге модели:

- `person.id` уникален, назначается один раз (`uid()`), никогда не
  переиспользуется и не меняется.
- `*LinkedId` (`fatherLinkedId`, `motherLinkedId`, `spouseLinkedId`,
  `linkedId` у sibling/child) — либо пустая строка, либо валидный `id`
  существующей записи в `persons`. Текстовые ФИО-поля рядом — это «снимок»
  на момент связывания, не источник истины и не обновляются автоматически
  при редактировании связанной персоны (см. Backlog).
- `*DocPages` — всегда массив (может быть пустым), никогда не `null`/
  `undefined`; каждый элемент — `{imageId, imageName, transcription}`, где
  `imageId` либо пусто, либо ссылается на реально существующую запись в
  object store `images`.
- `marriages[]` — персона может иметь **несколько** браков, это не опечатка
  и не legacy-поле; UI и модель это учитывают повсеместно.
- `isLateral` — визуальный/навигационный маркер («боковая ветвь»), не влияет
  на связи в модели и не меняет семантику `*LinkedId`.
- `avatarThumb` — всегда маленькая base64-миниатюра или пустая строка,
  никогда не полноразмерное изображение (то живёт в `images` store по
  `avatarImageId`).
- Любое новое поле, добавляемое в модель, должно попадать в
  `migrate*()`-функцию с дефолтным значением — записи, созданные до
  добавления поля, не должны падать при чтении.


```js
{
  id, personIndex, generation, isLateral,
  lastName, firstName, patronymic, gender, estate,

  // Рождение
  birthDateApprox, birthDate, birthYearFrom, birthYearTo, birthPlace,
  birthDocName, birthDocId, birthDocPath,
  birthDocPages: [{imageId, imageName, transcription}],   // МНОЖЕСТВО страниц
  birthDocArchive, birthDocFund, birthDocOpis, birthDocDelo, birthDocList,

  // Родители (могут быть текстом ИЛИ связаны с реальной персоной в базе)
  fatherLastName, fatherFirstName, fatherPatronymic, fatherEstate, fatherLinkedId,
  motherLastName, motherFirstName, motherPatronymic, motherEstate, motherLinkedId,

  // Крёстные
  godfatherLastName, godfatherFirstName, godfatherPatronymic, godfatherPlace,
  godmotherLastName, godmotherFirstName, godmotherPatronymic, godmotherPlace,

  // Аватар — ссылка на blob, не сам blob
  avatarThumb, avatarImageId, avatarImageName,

  siblings: [{linkedId, lastName, firstName, patronymic}],
  residences: [ "строка" ],
  children: [ mkChild() ],
  marriages: [ mkMarriage() ],   // МНОЖЕСТВЕННЫЕ браки, не один
  documents: [ mkDoc() ],         // произвольные прикреплённые документы (вкладка «Архив»)
  memories: [ mkMem() ],

  military: mkMilitary(),

  // Смерть
  deathDateApprox, deathDate, deathYearFrom, deathYearTo,
  deathPlace, burialPlace, deathCause,
  deathDocName, deathDocId, deathDocPath,
  deathDocPages: [{imageId, imageName, transcription}],
  deathDocArchive, deathDocFund, deathDocOpis, deathDocDelo, deathDocList,

  createdAt, updatedAt
}
```

### `mkMarriage()`
```js
{
  id, marriageDate, marriagePlace, marriageEnded, marriageEndDate, marriageEndReason,
  spouseLastName, spouseFirstName, spousePatronymic, spouseLinkedId,
  marriageDocName, marriageDocId, marriageDocPath,
  marriageDocPages:[{imageId, imageName, transcription}],
  marriageDocArchive, marriageDocFund, marriageDocOpis, marriageDocDelo, marriageDocList
}
```

### `mkChild()`
```js
{
  id, linkedId, firstName, lastName, patronymic, gender, estate,
  birthDateApprox, birthDate, birthYearFrom, birthYearTo, birthPlace,
  birthDocName, birthDocId,
  birthDocPages:[{imageId, imageName, transcription}],
  birthDocArchive, birthDocFund, birthDocOpis, birthDocDelo, birthDocList
}
```

### `mkDoc()` (произвольный документ, вкладка «Архив»)
```js
{ id, docId, name, transcription, comment, path, archive, fund, opis, delo, list,
  pages:[{imageId, imageName, transcription}], createdAt }
```

### `mkMem()` (воспоминание)
```js
{ id, lastName, firstName, patronymic, date, text }
```

### `mkMilitary()`
```js
{ unit, rank, position, serviceFrom, serviceTo, conflict, wounds, awards, death,
  pages:[{imageId, imageName, transcription}], docId, archive, fund, opis, delo, list }
```
**Изменение с v2.7**: у `military` теперь ЕСТЬ собственное поле `docId`
(добавлено в форму как `mil_docid`, в миграцию, в `colForm()`
автоприсвоение и в имя файла при экспорте) — старое ограничение из
предыдущей версии документа («у military нет своего ID») больше не
актуально.

**Важно про `*DocPages`**: многостраничные документы — массив
`{imageId, imageName, transcription}` на каждый раздел (рождение, смерть, брак,
ребёнок, произвольный документ, военная служба). `resolvePages(p, path)`
(п.5) — единая точка доступа к нужному массиву страниц по персоне `p` и
строковому пути (`'b'`, `'d'`, `'mil'`, `'mr'+i`, `'c'+i`, `'a'+i`).

**`linkedId` / `fatherLinkedId` / `motherLinkedId` / `spouseLinkedId`** — явные
связи между записями `persons` по `id`, поверх текстовых полей ФИО. Текстовые
поля остаются как «снимок» на момент связывания и не обновляются автоматически
при редактировании связанной персоны (см. Технический долг).

## 7. Development Rules

«Конституция разработки» — не описание того, что есть, а то, как принято
действовать. Читать перед любой архитектурной правкой.

### 7.1 Incremental Refactoring

- **Не смешивать рефакторинг и разработку новых функций.** Каждая новая
  функциональность сначала реализуется в существующем стиле; переносится в
  Core-слой отдельным шагом, если/когда до неё дойдёт очередь рефакторинга.
- Любое изменение должно помещаться в схему: **описание → выделение функции
  → Node-тест → замена вызова → удаление старого кода.** Если изменение
  нельзя разложить на независимые шаги такого вида — оно слишком большое,
  дробить дальше.
- **DOM не рефакторится без необходимости.** UI-код (открытие модалок,
  рендер дерева, переключение вкладок) непроверяем автоматически
  (Playwright недоступен) — трогать только при реальной необходимости
  (баг/фича), не «из эстетических соображений».

### 7.2 Pure Functions & Side Effects

- **Чистая функция = никаких скрытых зависимостей.** Не обращается к
  глобальным переменным, DOM, `Date.now()`/`new Date()`, `Math.random()`,
  `IndexedDB`, `localStorage`, `fetch`. Все входы — параметры, весь выход —
  возвращаемое значение.
- Это идеал; не применять его догматически к тривиальным фабрикам
  (`mkP`/`mkDoc` используют `uid()`/`new Date()` — переписывать их на
  инжектируемые time/random ради чистоты не нужно, выигрыш не окупает риск
  правки во всех точках вызова).
- Побочные эффекты допускаются только в местах, перечисленных в разделе 4.5
  («Границы побочных эффектов»). Новый побочный эффект вне этого списка —
  повод либо перенести его в существующий слой, либо осознанно расширить
  таблицу 4.5, но не оставлять неучтённым.

### 7.3 Shim Migration

- **Никогда не делать big-bang rename/переезд.** Любое масштабное
  переименование, перенос состояния или смена API — только через
  shim-переход: новый слой → совместимость со старым → `grep` на оставшиеся
  вхождения → визуальная проверка ключевых сценариев → удаление старого
  слоя. Правило без исключений, не только для `AppState`.

### 7.4 Testing

- **Extract → Test, всегда парой.** Ни одна функция не считается
  перенесённой в Core, пока не появился Node-тест на извлечённом (не
  переписанном вручную) коде.
- Любая логика, которую можно проверить без браузера (экспорт, импорт,
  GEDCOM, поиск, дедупликация, миграции, вычисления) — обязана проходить
  через Node-харнесс, а не считаться проверенной «на глаз».
- **После любого изменения модели данных** — обязательно прогонять
  export→import через Node-харнесс на реальных данных (раздел 4.6:
  `/mnt/project/data.json`), не только на синтетических.

### 7.5 Naming

- Именование остаётся в текущем стиле проекта (короткие глагольные имена:
  `colForm`, `renderList`, `mkP`) — не переименовывать существующие функции
  «ради единообразия» без реальной причины; каждое переименование само по
  себе подпадает под правило shim-перехода (7.3) и стоит риска, который
  нужно явно обосновать.
- Новые Core-функции, если это осмысленно, называть по образцу существующих
  сервисных группировок (`build*` — конструирует объект/структуру, `find*`/
  `resolve*` — читает без изменений, `apply*`/`create*` — мутирует/пишет) —
  чтобы будущая LLM-сессия могла предсказать поведение по имени, не читая
  тело.

### 7.6 State Rules

- Всё разделяемое состояние живёт в объекте `AppState` (объявлен один раз в
  начале скрипта): `all`, `cur`, `isNew`, `editMode`, `activeTab`,
  `pendingDupes`, `dupeResolutions`, `_pickPath`/`_pickIdx`,
  `_linkCallback`/`_linkCtx`, пан/зум дерева (`_t*`) и лайтбокса (`lb*`),
  `pendingImport`/`pendingImportZip`, `parsedGED`. **Новое разделяемое
  состояние добавлять только туда**, отдельные глобальные `let` не заводить.
- В `AppState` переносить только состояние, которое
  реально разделяется между несколькими функциями/подсистемами. Локальные
  переменные внутри одной функции в `AppState` не выносить.

### 7.7 Documentation Rules

- **Документация обновляется в конце каждой сессии**, где менялся код —
  версия, Changelog (раздел 11), Backlog/Roadmap (разделы 9–10), при
  архитектурных изменениях — Architecture/Core Registry (разделы 4–5).
  Отставание документации от кода — технический долг №1 для этого проекта
  (уже случалось дважды: разрыв v2.5-документации при v2.8-коде, закрыт
  2026-07-27; и потеря раздела Changelog при реструктуризации, закрыта
  2026-07-28 этой же правкой).

## 8. Architecture Decisions

Короткие записи, не полноценные ADR — что решено и почему, чтобы новая
сессия не предлагала это же заново.

**Почему HTML остаётся однофайловым.**
Нет сборки, нет зависимостей окружения — Дмитрий просто открывает файл в
браузере. Любой build-step увеличивает дистанцию между «что в файле» и «что
работает у пользователя», а у проекта и так нет постоянной памяти, чтобы
удерживать это в голове между сессиями.

**Почему IndexedDB, а не сервер/файловая БД.**
Offline-first, большие бинарные Blob'ы (сканы документов) хранятся
эффективно, не нужен бэкенд для личного однопользовательского инструмента.

**Почему нет фреймворка (React/Vue/etc).**
Масштаб проекта не оправдывает накладные расходы сборки. Отдельно для
LLM-разработки: явный код без слоёв абстракции фреймворка надёжнее
воспроизводится сессией без памяти, чем идиоматичный framework-код, паттерны
которого нужно держать в контексте целиком.

**Почему `AppState` — решено, но ещё не сделано.**
Устраняет главный источник неявных зависимостей (россыпь глобальных
переменных). Отложено до отдельного шага именно потому, что затрагивает
почти весь файл — делать только через shim-переход (правило 7.3), не
одной правкой.

**Почему миграции состояния — только через shim, без исключений.**
Big-bang rename опасен именно в проекте без continuous memory: сессия,
которая начала переезд, может не закончить его в рамках одного чата, и
следующая сессия унаследует наполовину мигрированный код без явного маркера
«это временное состояние». Shim делает промежуточное состояние легитимным и
безопасным сколь угодно долго.

**Почему Node Harness, а не Playwright.**
Сетевые ограничения контейнера Claude не дают установить браузерный
драйвер. Следствие — весь UI-код (DOM) непроверяем автоматически; отсюда
жёсткое разделение Core/DOM и приоритет извлечения именно чистой логики.

**Почему Repository/EventBus/плагинная архитектура — отложены.**
Repository оправдан при смене хранилища или синхронизации — этого не
предвидится. EventBus решает проблему, которой пока нет (немного мест
вызова `render*` после мутации, все explicit) — явные orchestration-цепочки
(`savePerson → finalizeSave → renderList`) понятнее для сессии без памяти,
чем неявная подписка на события. Плагины/расширяемость — нет ни второй
интеграции, ни команды, которая бы их писала.

## 9. Backlog

Технический долг и функциональные задачи — вместе, это один список
«что стоило бы сделать», а не разделение на два по формальному признаку.

### Технический долг

1. **Текстовые ФИО-поля родителей/супругов не синхронизируются
   автоматически** при редактировании связанной персоны (только при явном
   связывании через `*LinkedId` в момент выбора). Если Дмитрий переименует
   персону, у которой уже есть `fatherLinkedId`-связь с другими, текстовые
   копии ФИО у «детей» устареют. Не устранять point-fix'ом — рассмотреть
   при унификации модели (Roadmap, Этап 5, Cleanup).
2. `treeResetView()` — мёртвая функция с v2.4 (кнопка убрана, функция
   осталась; статус `Deprecated` в Реестре, раздел 5). Кандидат на удаление
   на Этапе 5, не раньше.
3. **Модалки/диалоги** реализованы несколькими разными способами
   (`dupeModal`, `dbModal`, `slinkModal`, `lb`/лайтбокс, `tree-overlay`) без
   общего API. Не унифицировать сейчас — низкий приоритет, риск/выгода не в
   пользу изменения на этом этапе (Roadmap — явно отложенный пункт).
4. **GEDCOM импорт** не проставляет `personIndex` (по дизайну), не
   переносит `marriages[]`/`military` полноценно — проверять
   `gedParseFam`/`gedParseIndi` перед использованием на реальном
   GEDCOM-файле, если он вообще появится в практике Дмитрия.

### Функциональное

1. **UI/UX-переработка** — конкретики от Дмитрия пока нет; при следующем
   запросе на эту тему — один уточняющий вопрос (какие экраны/сценарии
   болят больше всего), не додумывать.
2. Дмитрий, вероятно, всё ещё держит старый ~119.5 МБ export-JSON от v2.2
   (инлайновый base64 `_imgs`) — можно предложить импортировать его разово
   (backward-compat путь сработает) и пере-экспортировать уже компактным
   `.zip`.

## Аутентификация и управление пользователями (Lovable Cloud, 2026-08)

Добавлено в React-версии (не в legacy HTML). Стек: Lovable Cloud (Supabase Auth).

**Методы входа:** email + пароль, Google, Apple (управляемые OAuth-учётные
данные Lovable Cloud). Страницы: `/auth` (вход/регистрация/восстановление),
`/reset-password` (установка нового пароля по recovery-ссылке).

**Модель данных:**
- `public.profiles` — id (FK auth.users), display_name, email, avatar_url,
  is_blocked. Профиль создаётся триггером `handle_new_user` при регистрации.
- `public.user_roles` — роли (`admin`, `user`) в отдельной таблице;
  проверка через security-definer `has_role`. Первый зарегистрированный
  пользователь автоматически становится `admin`.
- RLS включён на обеих таблицах; `has_role` доступна только `authenticated`
  (предупреждение линтера 0029 — осознанное исключение, канонический паттерн).

**Маршруты:**
- Защищённые (layout `_authenticated/route.tsx`, `ssr: false`, редирект
  на `/auth`): `/` (база персон), `/profile`, `/admin/users`.
- Блокировка: если `profiles.is_blocked = true`, layout показывает экран
  «Доступ ограничен» и выполняет выход. Заблокировать себя нельзя.
- `/admin/users` — список пользователей (имя, email, роль, дата, статус),
  блокировка/разблокировка через server functions `listUsers` /
  `setUserBlocked` (`src/lib/users.functions.ts`, `requireSupabaseAuth` +
  проверка `has_role` внутри).

**Важно:** генеалогическая база остаётся в IndexedDB (локально в браузере) —
облако используется только для аккаунтов. Данные персон между устройствами
не синхронизируются; перенос — через экспорт/импорт ZIP.

**Ключевые файлы:** `src/routes/auth.tsx`, `src/routes/reset-password.tsx`,
`src/routes/_authenticated/route.tsx`, `src/routes/_authenticated/profile.tsx`,
`src/routes/_authenticated/admin/users.tsx`,
`src/components/annuli/UserMenu.tsx`, `src/lib/users.functions.ts`,
`src/start.ts` (functionMiddleware: attachSupabaseAuth).
