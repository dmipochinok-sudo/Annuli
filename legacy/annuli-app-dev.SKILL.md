# Annuli — разработка приложения

Однофайловое HTML-приложение (весь CSS/JS инлайн, данные в браузерном
IndexedDB, без сервера). Ведёт генеалогическую базу данных семьи. Пользователь
(Дмитрий) нетехнический — делегирует все инженерные решения Claude, общается
кратко («продолжай»). Не задавай лишних уточняющих вопросов там, где решение
очевидно из контекста кода — действуй автономно и показывай результат.

## Обязательный первый шаг

**Прежде чем делать что-либо ещё — прочитай `references/ANNULI_PROJECT_DOCUMENTATION.md`
(рядом с этим SKILL.md, в подпапке `references/`).** Это самый свежий слепок
архитектуры проекта: модель данных, устройство IndexedDB, полный инвентарь
функций, известный технический долг и открытые задачи (включая экспорт медиа).
Без этого документа легко потратить время на повторный аудит того, что уже
задокументировано.

**После этого — обязательно перечитай актуальную версию самого HTML-файла
заново** (`view`/`grep`) — не полагайся только на документ и не полагайся на
память о структуре из прошлых сессий: версии меняются быстро и заметно, и
`ANNULI_PROJECT_DOCUMENTATION.md` тоже может немного отстать от реального кода
на момент текущего чата (если это так — после сессии стоит обновить и его).

## Быстрая ориентация в файле

```bash
# Найти актуальный список функций верхнего уровня
grep -oP "^function \K[a-zA-Z0-9_]+(?=\()" Annuli_vX_Y.html | sort -u

# Найти модель персоны
sed -n '/^function mkP()/,/^}/p' Annuli_vX_Y.html

# Найти версию схемы IndexedDB и её stores
grep -n "DBN=\|DBV=\|createObjectStore" Annuli_vX_Y.html

# Найти структуру вкладок формы
grep -n "const tabs=\[" Annuli_vX_Y.html
```

## Ключевые архитектурные факты (актуальны на момент последнего аудита, см. дату
в ANNULI_PROJECT_DOCUMENTATION.md — сверяй, могло измениться)

- IndexedDB `genealogy_db`, два store: `persons` (сами персоны) и `images`
  (`Blob`-изображения, адресуются `imageId`-строками, которые лежат внутри
  персоны в массивах `*DocPages[]` и в `avatarImageId`).
- Персона может иметь несколько браков (`marriages[]`), несколько детей,
  многостраничные документы (`birthDocPages`, `marriageDocPages`,
  `deathDocPages`, `military.pages`, произвольные `documents[]`).
- Связи между персонами — через `*LinkedId` (`fatherLinkedId`,
  `motherLinkedId`, `spouseLinkedId`, `linkedId` у детей/сиблингов) поверх
  текстовых ФИО-полей. Текст — «снимок», не живая ссылка: не обновляется
  автоматически при редактировании связанной персоны.
- Дедупликация не связанных вручную персон (`findPendingDuplicates` и
  окружение) срабатывает при сохранении и при импорте. Проверяет только
  ещё не связанных (`!linkedId`) детей/сиблингов/родителей/супругов — эта
  проверка обязана быть симметричной для всех пяти ролей (отец/мать/сиблинг/
  ребёнок/супруг), иначе уже связанные родственники будут предлагаться заново
  при каждом сохранении (был реальный баг, исправлен в v2.4 — см. документ,
  раздел 7.2, как пример класса ошибок, за которым надо следить при правках
  этой функции).
- `exportDB()` с версии 2.3 экспортирует ZIP-архив с текстом (`data.json`) и
  полноразмерными медиа (`images/`), см. раздел «Данные» ниже и документ
  проекта, раздел 6 — подробности именования файлов, backward-compat импорта
  и покрытия тестами.

## Рабочий процесс правок

1. Скопировать текущий HTML в `/home/claude/` как рабочий файл.
2. Точечные правки — Python-скриптом с функцией вида
   `rep(label, old, new)` для точного строкового replace, либо
   инструментом `str_replace`. После каждой правки — проверять баланс
   скобок в JS/CSS и синтаксис через `node -e "new Function(...)"` на
   извлечённом содержимом `<script>`.
3. Для логики, которую нельзя тривиально проверить чтением кода (экспорт/
   импорт, дедупликация, парсинг GEDCOM, вычисление имён файлов и т.п.) —
   **не полагаться на Playwright** (недоступен в контейнере Claude из-за
   сетевых ограничений). Вместо этого: извлечь нужные функции из реального
   HTML-файла построчным поиском парных скобок (см. пример подхода в
   документе проекта, раздел 6 — "Тестирование"), прогнать в изолированном
   Node-харнессе с фейковыми `document`/`imgGet`/`imgPut`/`dbPut` и т.п.
   Так тестируется ровно тот код, что уходит в прод, без переписывания вручную.
4. Готовый файл — в `/mnt/user-data/outputs/Annuli_vX.Y.html` с явным
   инкрементом версии; версию дублировать в `<title>` или в комментарии
   в начале `<script>`, чтобы имя файла и код не расходились (в прошлом
   были случаи расхождения — см. документ проекта).
5. `present_files` в конце, без лишних преамбул.

## Данные

С версии 2.3 `exportDB()` создаёт **`Annuli_YYYY-MM-DD.zip`** (через встроенный
инлайн JSZip, без CDN): `data.json` внутри архива — `{app, version, exportDate,
count, persons:[...]}` (текст + `avatarThumb`-миниатюра, БЕЗ base64-картинок),
плюс папка `images/` с полноразмерными Blob'ами в исходном формате, названными
по номеру документа в базе (`birthDocId`/`marriageDocId`/`docId` и т.п., с
фолбэком на `personIndex.<раздел>` если ID ещё не назначен, `_2`/`_3` для
многостраничных документов). Каждая страница/аватар в экспортируемом JSON несёт
временное поле `_file` с путём внутри архива — оно снимается (`stripImportHelperFields`)
сразу после восстановления Blob'ов при импорте и не сохраняется в IndexedDB.
Импорт (`prepImport`/`doImport`) принимает и `.zip` (новый формат, восстанавливает
`images` store через `restoreImagesForPerson`), и старый `.json` с инлайновым
base64 `_imgs` (versions ≤2.2, backward-compat путь через `dataURLtoBlob2`), и
совсем старый `.json` без картинок вообще (только текст+миниатюра — тогда
`imageId`/`avatarImageId` внутри персон будут «висячими» ссылками, если открывать
не в исходном браузере/устройстве).
